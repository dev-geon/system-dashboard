# system-dashboard

코드 레포에서 **시스템 구조를 한 장으로 보는 HTML 대시보드**를 만든다. 팀 개발문서로 쓰는 것이 목적이라, 예쁜 그림보다 **처음 보는 사람이 오해 없이 읽는 것**이 우선이다.

## 무엇이 나오나

```
docs/architecture/
├── dashboard.md     ← 원본. Mermaid 텍스트라 diff가 읽히고 사람이 고친다
└── dashboard.html   ← 빌드 결과. 더블클릭으로 열리고 그대로 전달한다
```

화면 구성: **AS IS ▶ TO BE(맨 위 — AS IS의 한계, TO BE의 이점)** → **성능 비교 표(수치만)** → 관점 탭(탭 이름은 차트 이름만 — 시스템 아키텍처·플로우차트…; 탭 하나에 그림 하나 — 글자 제목 없이 그림, 범례, 흐름도면 오른쪽에 경로별 예시 카드) → **작업 Jira**(Initiative 등 티켓 번호·타이틀, 실제 Jira 링크). 푸터는 없다. 읽는 순서가 곧 "무엇이 바뀌나 → 어떻게 동작하나"다. 화면 제목 머리·요약 숫자 카드·범위와 한계 절은 두지 않는다.

## 왜 이렇게 만드나

- **관점별로 나눈다.** 모든 것을 한 장에 넣은 "마스터 다이어그램"은 거의 항상 읽히지 않는다. 런타임·배포·업무 흐름은 각각 다른 이야기라 탭을 나눈다.
- **무엇을 뺄지는 사람이 정한다.** 코드에서 자동으로 뽑은 구조는 빠짐없지만 초점이 없다. Claude는 근거가 달린 후보를 내고, 그릴 관점과 뺄 것은 사람이 확정한다.
- **규칙은 스크립트가 판정한다.** "이름+타입 라벨", "연결 없는 박스 금지" 같은 규칙을 눈으로 점검하면 매번 빠진다. `check_diagrams.py`가 매번 같은 결과를 낸다.
- **원본은 텍스트다.** 그림 파일은 코드와 함께 갱신되지 않는다. Mermaid 텍스트는 같은 커밋에서 고칠 수 있다.
- **바뀌는 것을 먼저 보여 준다.** 구조도를 찾는 사람은 대개 "무엇이 달라지나"를 묻는다. AS IS ▶ TO BE를 첫 화면에 두고, 그림은 그 근거로 읽힌다.

## 절차

### 1. 읽을 사람을 묻는다

추상화 수준이 여기서 정해진다. 사용자가 말하지 않았으면 한 줄로 묻는다.

| 읽을 사람 | `level` | 박스 단위 |
|---|---|---|
| 경영진·타 부서 | `context` | 시스템 전체와 외부 사용자·외부 시스템 |
| 신규 입사 개발자 | `container` | 앱·서비스·DB·큐 (기본값) |
| 디버깅하는 개발자 | `component` | 서비스 안의 모듈·핸들러 |

### 2. 레포를 훑어 후보를 만든다

아래를 찾아 **후보 목록**을 만든다. 후보마다 근거 파일 경로를 단다 — 근거 없는 박스는 사람이 검증할 수 없다.

- 진입점과 앱 단위: `package.json`·`pyproject.toml`·`*.csproj`·`go.mod`, `main`/`Program`/`app` 파일, 모노레포의 `apps/`·`services/`
- 서비스 간 호출: HTTP 클라이언트 생성부, base URL 환경변수, gRPC 스텁
- 저장소: DB 연결 문자열·ORM 설정·마이그레이션 폴더, 캐시·스토리지 클라이언트
- 비동기: 큐·토픽 이름, 발행/구독 코드 (브로커만 쓰지 말고 **토픽 이름까지**)
- 배포: `Dockerfile`, `docker-compose*`, CI 워크플로, IaC(`*.bicep`·`*.tf`·k8s yaml)
- **경로별 실제 사례(흐름도용):** 처리 흐름이 갈리는 시스템이면, 각 갈래를 실제로 탄 사례를 함께 모은다 — 로그·테스트 케이스·실험 결과·이슈·VOC. 사례마다 출처(파일·ID)와 결과 수치를 단다. 흐름도의 예시 카드(L3)가 여기서 나온다

레포가 아니라 문서·실험 결과만 주어지면(예: 실험 보고서와 결과 JSON) 같은 항목을 그 자료에서 찾고, 근거 칸에 문서 경로를 적는다.

후보는 표로 보여 준다: `구성요소 · 타입 | 근거 파일 | 연결 대상 | 제안 관점`. 코드에서 확인 못 한 것은 지어내지 말고 "미확인"이라고 표에 적는다.

### 3. 사람이 확정한다

- 그릴 관점 고르기 (최대 5개): `context` 전체 맥락 · `runtime` 실행 구조 · `sequence` 시퀀스 · `flow` 업무 흐름 · `deploy` 배포
- 뺄 것, 빠진 것, 미확인 후보를 그릴지
- 이 작업의 Jira 티켓 — Initiative와 그 아래 작업 티켓의 번호·타이틀(Jira `https://<사이트>.atlassian.net/browse/<키>`). 확인한 것만 적는다
- AS IS ▶ TO BE(히어로)에 쓸 내용 — AS IS는 지금 방식이 무엇에 의존하고 무엇이 문제인지, TO BE는 바뀌면 생기는 이점 — 그리고 성능 비교 표에 넣을 지표와 그 출처 — 바뀌는 것이 없는 현황 문서면 둘 다 생략
- `flow`를 골랐다면 **경로마다 어느 사례를 예시로 쓸지** 2단계 후보에서 고르게 한다. 잘된 사례만 고르지 않는다 — 효과가 없었거나 실패한 갈래가 있으면 그것도 한 장
- 구조와 흐름이 둘 다 중요하면 **구조도(무엇이 있나) + 흐름도(어떻게 흐르나)를 짝으로** 제안한다. 둘의 박스 이름을 같게 맞춰 서로 찾아 읽히게 한다
- 이 단계 없이 4로 넘어가지 않는다. 사람이 고르지 않은 관점은 그리지 않는다.

### 4. `dashboard.md`를 쓴다

`assets/dashboard.example.md`를 복사해서 시작한다. 쓰기 전에 규칙과 도형을 확인한다.

- 다이어그램 규칙 D1~D8 → `references/diagram-rules.md`
- 도형·화살표·관점 종류 F1~F4 → `references/symbols.md`
- 화면 레이아웃·AS IS ▶ TO BE 문안(L1)·설명 문단 금지(L5)·성능 표 출처(L6) → `references/layout.md`

핵심 표기만 요약하면:
- **패널에는 글자 제목이 없다.** 탭(차트 이름)과 그림이 말한다. 관점 제목(`## view: 종류 | 제목`의 제목)은 선택이고 보조기술 설명으로만 쓰인다. 그림만 봐도 이해되게 그리고, **설명 문단은 쓰지 않는다**(L5) — 꼭 알릴 단서는 예시 카드에
- **흐름도에는 경로마다 실제 예시를 붙인다(L3).** 끝 단말을 `A · …`, `B · …` 처럼 배지로 시작하고, 그림 아래 `### 예시` 에 `- **A** <경로> — "<실제 질문·사례>" → <무슨 일이 일어났나>` 를 경로마다 하나씩. 예시는 지어내지 말고 실제 기록(로그·실험 결과·티켓)에서 가져온다
- **순서와 조건(언제 무엇을 하나)이 핵심이면 구조도가 아니라 `flow`(흐름도)로 그린다.** 구조도에 ①②③ 순번을 달면 흐름도처럼 읽히는데 분기가 안 보여 오해를 부른다
- `## asis-tobe | <비교 제목>` 아래 `### AS IS` · `### TO BE` — **AS IS는 한계, TO BE는 이점을 4줄·200자 이내로. 성능 수치는 넣지 않는다**(L1, 숫자가 있으면 WARN)
- `## jira | 작업 Jira` — `- [SHOP-100](https://example.atlassian.net/browse/SHOP-100) 타이틀 — Initiative` 목록(L7). 화면 맨 아래
- `## compare | <표 제목>` — `| 지표 | AS IS | TO BE | 변화 |` 표 + `출처: …` 줄(L6). 수치는 모두 여기로, 출처 값 그대로
- 구조도 박스 라벨은 `이름 · 타입` (예: `"Orders Table · PostgreSQL"`)
- **구조도는 흐름도와 다르게 그린다.** 도형은 사람 `([ ])` · 앱·서비스·도구 `[ ]` · 외부 시스템 `[[ ]]` · 저장소 `[( )]` 만(순서도 기호 금지), 계층은 `subgraph`로 나누고, 새로 넣는 부분은 `class … added`. 화면은 계층을 왼쪽→오른쪽 칸으로, 선은 직선(직각)으로 그린다 → `references/symbols.md` "구조도 도형"
- 화살표 모양이 뜻이다: `-->` 동기 요청 · `-.->` 비동기 이벤트 · `==>` 데이터 흐름. 라벨은 `-->|라벨|` 형식만
- 박스마다 `click id "레포 파일 URL"`로 코드에 연결한다 (URL은 `ref` 커밋 기준)

### 5. 검사한다

`<스킬 폴더>`는 이 SKILL.md 가 있는 폴더다(스킬을 불러올 때 알려 주는 기본 디렉터리). 표준 라이브러리만 쓰는 Python 3.9+ 스크립트라 설치할 것이 없다.

```bash
python3 <스킬 폴더>/scripts/check_diagrams.py docs/architecture/dashboard.md
```

FAIL이 0이 될 때까지 고친다(종료 코드 0). WARN은 사람에게 보여 주고 남길지 묻는다 — WARN을 없애려고 사실과 다른 그림을 그리지 않는다.

### 6. 빌드하고 눈으로 확인한다

```bash
python3 <스킬 폴더>/scripts/build_dashboard.py docs/architecture/dashboard.md
```

- 빌드는 검사를 다시 돌리고 FAIL이 있으면 멈춘다.
- 결과 HTML을 브라우저로 열어 **모든 탭**을 넘겨 보고 스크린샷으로 확인한다. 다이어그램이 겹치거나 잘리면 원본에서 방향(`TB`/`LR`)이나 관점 분할을 바꾼다.
- 다이어그램은 열 때 CDN의 mermaid.js(버전 고정)로 그려진다. 오프라인이면 Mermaid 소스가 그대로 보이고 화면에 그 사실이 적힌다.

### 7. 사람 승인

열 경로(`file:///…/dashboard.html`)를 그대로 제시하고, 예시 카드마다 쓴 사례의 출처, 남은 WARN, 그리지 않은 것과 코드에서 확인하지 못한 것을 **답변으로** 함께 알린다(화면에는 두지 않는다).

## 하지 않는 것

- 사람이 고르지 않은 관점을 추가하지 않는다. 빠진 게 있어 보이면 제안만 한다.
- 코드에서 확인하지 않은 구성요소·연결을 그럴듯하게 채우지 않는다. 그리지 말고 7단계에서 사람에게 알린다.
- 애니메이션을 넣지 않는다. 화살표 방향을 반복할 뿐 정보가 없다.
- HTML을 손으로 고치지 않는다. 고칠 것은 `dashboard.md`에서 고치고 다시 빌드한다.
