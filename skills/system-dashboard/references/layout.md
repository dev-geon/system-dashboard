# 화면 레이아웃

참조: 제안서 슬라이드 「AS IS / TO BE」(흰색·파란색 반반 분할, 가운데 흰 삼각형 홈, 아래쪽 가는 선 + 문서명 + 쪽 번호).

화면 틀은 `assets/dashboard.template.html`에 있고 `build_dashboard.py`가 채운다. 색·간격을 바꾸려면 템플릿의 `:root` 토큰만 고친다 — 다이어그램 색도 같은 토큰을 읽어서 함께 바뀐다.

## 순서

```
┌ AS IS ▶ TO BE (맨 위 · 반반 분할 · AS IS 한계 / TO BE 이점) ──────────┐
├ 성능 비교 표 ─ 지표 | AS IS | TO BE(파란 강조) | 변화(칩) | 예시(선택) ──┤
├ 이관 안내 (프로젝트 단위 이관일 때만) ─ AS IS 카드 ─[이동 방식]▶ TO BE 카드 × 역할 쌍 ─┤
├ 관점 탭 ─ [시스템 아키텍처] [플로우차트] … (차트 이름만, 모서리 12px = 카드) ──┤
│   다이어그램 — 구조도: 계층 칸(좌→우) + 카드 + 직각 직선 / 흐름도·시퀀스: Mermaid │
│   범례 (이 관점에서 쓴 도형·화살표만)                            │
│   예시 카드 (흐름도) ─ 그림 오른쪽에 세로로 [A] 경로 · "실제 질문" · 결과 │
├ 질문별 답 (A/B·실험 기록이 있을 때만) ─ 질문마다 접는 줄 ▸ AS IS 답 | TO BE 답 ─┤
└ 작업 Jira ─ [SHOP-100] 타이틀 · Initiative / [SHOP-112] 타이틀 · Story … (번호 = 실제 링크) ┘
```

읽는 순서: **무엇이 바뀌나(AS IS ▶ TO BE) → 어떻게 동작하나(관점 탭)**. 화면 제목 머리·결론 한 줄·요약 숫자 카드·범위와 한계 절·구성요소 목록 표는 두지 않는다(설계 결정). 푸터(메타 정보·문서 제목·쪽 번호)도 두지 않는다 — 문서 제목(`title`)은 브라우저 탭 이름과 보조기술용 제목에만 쓴다. 머리말의 읽을 사람·수준·레포·기준일은 원본과 검사에만 쓰인다.

## 탭과 패널 · L5 설명 문단 없음 (WARN)

탭에는 **차트 이름만** 나온다 — 시스템 아키텍처(context·runtime) · 배포 아키텍처 · 시퀀스 다이어그램 · 플로우차트. 같은 종류가 둘이면 번호가 붙는다. 탭 모서리는 카드와 같은 12px.

패널에는 **글자 제목도 설명도 없다** — 탭 이름과 그림이 말한다(설계 결정). 관점 제목(`## view: 종류 | 제목`)은 선택이며 화면 낭독기용 설명으로만 붙는다. 관점 아래 설명 문단은 화면에 나오지 않는다(있으면 WARN L5) — 배포 전·실험 조건 같은 꼭 필요한 단서는 예시 카드에 짧게 넣는다. 그림이 실제로 그 종류처럼 읽히는지 확인한다 — 구조도에 순번을 달아 흐름처럼 읽힌다면 `flow`로 다시 그린다.

## L3 · 흐름도는 경로마다 예시를 붙인다 (WARN)

흐름도만 보면 "그래서 실제로 어떤 질문이 어느 길로 가나"가 안 보인다. 끝 단말마다 실제 사례 하나를 카드로 붙인다.

```
flowchart TB
  ...
  done(["A · 주문 완료"])
  wait(["B · 입고 대기 안내"])
```

```
### 예시
- **A** 재고가 있을 때 — "무선 이어폰 1개 주문" → 결제 모듈을 거쳐 주문 완료까지 간다
- **B** 품절일 때 — "한정판 키보드 주문" → 결제 없이 입고 대기 안내로 끝난다
```

- 끝 단말 라벨을 `<배지> · ` 로 시작하면(배지는 1~3자) 같은 배지의 예시가 있는지 본다. 없으면 WARN
- `### 예시` 자체가 없으면 WARN
- 형식 `- **<배지>** <경로 이름> — "<질문·사례>" → <결과>` 이면 카드로 나눠 그린다. 다르면 한 줄 카드로
- 화면: 흐름도 그림은 왼쪽, 예시 카드는 오른쪽에 세로로 나란히 — 경로 배지를 그림과 바로 맞대어 읽는다. 900px 미만이면 그림 아래로 내려간다
- **예시는 실제 기록에서 가져온다.** 지어낸 예시는 그림이 맞다는 착각을 만든다. 숫자는 기록 값 그대로
- **카드에는 뜻만 쓴다.** 테스트 이름·티켓·수용 기준 번호·파일 경로·커밋 해시는 쓰지 않는다 — "어떤 상황에서 무슨 일이 일어났나"로 풀어 쓰고, 어느 기록인지는 7단계 답변으로 알린다(L6)

## 구조도 화면 · L4 계층·폭 (WARN)

구조도는 흐름도처럼 보이면 안 된다 — 흐름도는 위→아래로 단계가 이어지고, 구조도는 **왼쪽→오른쪽 계층 칸**에 카드가 놓인다.

- 칸: `subgraph` 하나가 한 칸. 칸 이름은 칸 위에 파란 굵은 글자. 칸 바탕은 `--bg`, 테두리 `--line`
- 카드: 타입 아이콘 + 굵은 이름(15px·800) + 작은 타입 글자 + 오른쪽 위 구성요소 종류. 카드는 링크하지 않는다(누르면 화면을 떠나 읽던 흐름이 끊긴다)
- 새 부분(`class … added`): 파란 카드(`--brand-fill`, 흰 글자) — 맨 위 TO BE 와 같은 색이라 "이번에 바뀌는 것"이 바로 읽힌다. 그 카드에 닿는 선도 파란색
- 외부 시스템: 점선 테두리
- 선: 수평·수직 직선만, 칸 사이 통로의 줄기에서 직각으로 꺾는다. 통로 폭은 고정이 아니다 — 지나는 줄기 수(줄기 간격 16px)와 가장 긴 라벨 폭만큼 넓어진다(최소 72px)
- 라벨: 대상 카드 바로 앞 **라벨 구역**에 작은 상자로, 가지 위 대상 높이에. 줄기들보다 대상 쪽에 있어 다른 줄기를 덮지 않는다. 같은 카드로 여러 선이 들어오면 카드가 라벨 높이만큼 늘어난다
- 엇갈림: 줄기 순서를 엇갈림이 가장 적게 고르고, 남는 엇갈림은 바탕색 테로 한쪽을 끊어 보인다
- 같은 높이: 한 가장자리를 들고 나는 선은 높이를 나눠 쓰고, 서로 다른 카드의 수평 구간이 같은 높이로 겹치면 한쪽을 비킨다
- 너비: 화면 폭을 넘으면 라벨을 접고(최대 폭 168→96px), 그래도 넘으면 칸을 좁힌다(200→176px). 그래도 넘으면 그림 안에서만 가로로 스크롤된다. 1280px 이상 화면에서 그림 폭은 약 1,090px — 칸 3개는 넉넉하고, 4개부터는 통로 라벨이 짧아야 들어간다
- 폭 추정(WARN L4): 검사기가 렌더러의 가장 좁은 치수(칸 176px · 라벨 96px)로 폭을 어림해 1,090px 을 넘으면 알린다 — 칸을 합치거나(한 시스템의 진입·처리는 한 칸) 통로 라벨을 줄인다
- 계층 밖에 둔 카드는 WARN(L4) — "기타" 칸으로 모인다
- 칸을 건너뛰는 화살표, 같은 칸에서 사이에 카드를 두고 잇는 화살표는 WARN(L4) — 선이 카드를 지나간다

## 맨 위 · AS IS ▶ TO BE

`## asis-tobe | <비교 제목>` 절 아래 `### AS IS`, `### TO BE` 두 소절을 둔다. 있으면 화면 **맨 위**에 나온다 — 이 대시보드가 무엇을 바꾸는지가 가장 먼저 보여야 한다. 바뀌는 것이 없는 순수 현황 문서면 생략하고, 그때는 관점 탭이 맨 위에 온다.

- 왼쪽 AS IS: 흰 바탕(`--surface`), 파란 제목과 본문
- 오른쪽 TO BE: 파란 바탕(`--brand-fill`), 흰 제목과 본문
- 경계 세로 가운데에 흰 삼각형 홈이 오른쪽을 가리킨다 — "지금 → 바뀔 모습". 좁은 화면에서는 위아래로 쌓이고 홈이 아래를 가리킨다
- **AS IS는 지금 방식의 한계, TO BE는 바뀌면 생기는 이점을 쓴다.** 무엇에 의존했고 무엇이 문제였나 → 무엇이 가능해지나. 결과 요약 한 줄이 아니라 이유가 읽혀야 한다
- **소절마다 4줄, 200자 이내.** 넘으면 WARN(L1)
- **성능 수치는 쓰지 않는다** — 숫자가 있으면 WARN(L1). 수치는 아래 성능 비교 표로 분리한다(설계 결정)
- 본문에 목록(`- `)을 써도 된다

## 성능 비교 표 · L6 화면에 출처를 쓰지 않는다 (WARN)

`## compare | <표 제목>` 절에 파이프 표 하나를 둔다. AS IS ▶ TO BE 바로 아래에 나온다.

```
## compare | 성능 비교

| 지표 | AS IS | TO BE | 변화 | 예시 |
|---|---|---|---|---|
| 주문 API 응답 시간 (p95) | 1.8초 | 0.3초 | −83% | 10월 1주차 같은 트래픽을 다시 흘렸을 때 |
```

- 머리줄의 `AS IS`·`TO BE`·`변화` 열을 알아본다 — TO BE 열은 파란 굵은 글자, 변화 열은 칩, AS IS 열은 흐리게
- AS IS·TO BE 칸은 줄을 바꾸지 않는다 — 값이 길면(14자 안팎을 넘으면) 표가 넓어져 오른쪽 열이 잘린다. 칸은 짧게 쓰고 풀이는 예시 열로 보낸다
- 머리가 `예시`·`사례`·`설명`·`비고` 인 열은 글자 열이다 — 줄을 바꾸고 왼쪽에 맞춘다. 지표마다 실제 사례(어떤 상황에서 무슨 일이 일어났나)를 한 줄씩 붙일 때 쓴다. 숫자만으로는 "무엇이 좋아졌나"가 와닿지 않는다
- 표가 없거나 열 수가 어긋나면 FAIL(P2)
- **수치는 측정 기록에서 그대로 옮긴다.** 반올림은 기록 값에서 한 번만, 변화율은 TO BE ÷ AS IS − 1
- 좋아진 지표만 고르지 않는다 — 나빠지거나 그대로인 지표도 있으면 같이 싣는다
- **출처는 화면에 쓰지 않는다(L6).** 파일 경로·`파일:줄`·커밋 해시·수용 기준 번호(AC-…)·테스트 이름·결과 파일명은 읽는 사람에게 뜻을 더하지 않고 문장만 무겁게 한다. 수치마다 어느 기록에서 왔는지는 3단계에서 사람과 확인하고 7단계 답변으로 알린다. 화면에 남기는 근거 링크는 맨 아래 작업 Jira 절 하나다
- WARN(L6): 표 아래 `출처:` 줄이 있을 때 · 표 칸·흐름도 예시·AS IS ▶ TO BE 에 파일 경로·`파일:줄`·커밋 해시·`AC-…` 번호가 있을 때(테스트 이름은 검사기가 알아보지 못하므로 쓰는 쪽이 챙긴다). 예전 원본의 `출처:` 줄은 빌드하면 표 아래 작은 글자로 나온다 — 지운다

## 이관 안내 · L8 (WARN)

AS IS ▶ TO BE 가 **프로젝트(레포) 단위 이동**이면 — 기능이 한 프로젝트에서 다른 프로젝트로 옮겨 가면 — 성능 비교 표 바로 아래에 이관 안내를 둔다. "어디에서 어디로, 무엇이 어떻게 옮겨 갔나, 무엇이 남나"를 한 장에서 답한다. 같은 레포 안의 구조 변경이면 쓰지 않는다.

```
## move | 이관 안내

- AS IS: shop-admin · PHP · Laravel
- TO BE: order-service · Go

| 항목 | AS IS | 이동 방식 | TO BE | 설명 |
|---|---|---|---|---|
| 주문 생성 | `app/Http/OrderController.php` | 바뀜 | `cmd/api/order_handler.go` | 동기 처리 → 접수 후 비동기 처리 |
| 금액 계산 | `app/Services/PriceCalc.php` | 포팅 | `internal/price/calc.go` | 반올림 규칙을 같게 |
| 결제 연동 | `app/Clients/PgClient.php` | 합침 | `internal/pay` 공용 클라이언트 | 재시도·타임아웃은 공용 규칙 |
| 주문 이력 | `orders_log` (MySQL) | 원천 변경 | `order_events` (PostgreSQL) | 과거 이력은 옮기지 않음 |
| 관리자 주문 화면 | `resources/views/orders` | 유지 |  | 이관하지 않음 — 새 화면 오픈 뒤 폐기 |

참고: 두 시스템이 함께 도는 기간의 운영 규칙은 명세 문서에
```

- 화면: **좌우 대응 지도.** 맨 위 머리 줄에 왼쪽 AS IS 프로젝트, 오른쪽 TO BE 프로젝트. 그 아래 역할마다 한 줄 — 왼쪽 흰 카드(항목 이름 + AS IS 위치) ─[이동 방식 칩]▶ 오른쪽 파란 카드(TO BE 위치 + 설명). 색은 맨 위 AS IS ▶ TO BE 와 같다
- 옮기지 않는 항목(`유지`·`폐기`)은 화살표가 점선이고 오른쪽이 점선 빈 카드 — 설명에 언제 어떻게 정리되는지 쓴다
- 위치는 글자로만 쓴다(링크하지 않는다). 파일명은 `코드` 표기로
- 이동 방식 낱말은 정해져 있다: 포팅(같은 동작을 다른 언어로) · 바뀜(동작이 달라짐) · 합침(새 쪽의 공용 부품으로) · 원천 변경(읽는 데이터가 달라짐) · 새로 · 유지 · 폐기
- 좁은 화면(720px 미만)에서는 카드가 위아래로 쌓이고 화살표가 아래를 가리킨다
- WARN(L8): 프로젝트 두 줄이 없을 때 · 항목·AS IS·이동 방식이 빈 줄 · 정해지지 않은 이동 방식 낱말 · TO BE 가 비었는데 `유지`·`폐기` 가 아닐 때 · 10쌍 초과
- 표가 없거나 `AS IS`·`이동 방식`·`TO BE` 열이 없거나 열 수가 어긋나면 FAIL(P2)

## 질문별 답 · L11

같은 질문을 AS IS·TO BE 로 돌려 본 기록(A/B 실행·실험 로그)이 있으면, 숫자 표와 사례 카드만으로는 "실제로 무엇이라고 답했나"가 보이지 않는다. `## answers | <제목>` 절에 질문 원문과 양쪽 답 원문을 그대로 둔다. 관점 탭 아래, 작업 Jira 위에 나온다.

`````
## answers | 질문별 답 전문

### 3E2615 2025 EU ETS 연간 배출량 알려줘
- AS IS: get_mrv_summary → get_mrv_summary · 23.4초 · 호출 2회
- TO BE: onto_resolve → query_cosmos → onto_check · 86.3초 · 호출 3회

````answer as-is
## 3E2615 · 2025 EU ETS 배출량: **8,209.47 tCO₂**
…(답 원문 그대로)
````

````answer to-be
…
````
`````

- 화면: 질문마다 접는 줄 하나(번호 · 질문). 펼치면 왼쪽 AS IS(흰 테두리), 오른쪽 TO BE(파란 테두리) 카드가 나란히 — 머리에 태그와 메타 줄, 아래 답 원문. 900px 미만이면 위아래로 쌓인다. 절 머리 오른쪽에 모두 펼치기·접기 버튼, 인쇄할 때는 모두 펼친다
- 답 원문은 마크다운 일부(제목·문단·굵게·기울임·코드·링크·목록 한 단 중첩·표·인용·구분선·코드 블록)로 그린다. 원문 HTML 은 실행되지 않고 글자로 보인다
- 답 펜스는 **백틱 4개 이상 + `answer as-is` / `answer to-be`** 로 열고 같은 수 이상의 백틱만 있는 줄로 닫는다 — 답 안에 `## 제목`·``` 코드 블록이 있어도 절이 끊기지 않는다. 한쪽 답만 있으면 한 칸으로 그린다
- 메타 줄(`- AS IS: …`·`- TO BE: …`)은 선택 — 부른 도구 순서·걸린 시간·호출 수처럼 기록에 있는 값만
- **답은 고치지 않는다.** 기록 원문 인용이라 L6(출처)·L9(직역)·L10(약어) 검사 대상이 아니다. 요약·발췌가 필요하면 성능 표 예시 열이나 흐름도 예시 카드에 쓴다
- **고른 질문만 넣지 않는다.** 그 실행의 질문을 전부 넣어야 비교가 기울지 않는다 — 좋은 답만 고르면 표의 합계와 맞지 않는다
- FAIL(P2): `### 질문` 이 없을 때 · 답 펜스가 질문 앞에 있거나 닫히지 않았을 때 · 펜스 정보가 `answer as-is|to-be` 가 아닐 때 · 답이 하나도 없는 질문. WARN(L5): 질문·메타·펜스 밖의 설명 글. WARN(L11): 항목 30개 초과

## 작업 Jira · L7 (WARN)

`## jira | 작업 Jira` 절에 이 작업의 Jira 티켓을 적는다. 화면 맨 아래, 푸터 자리에 나온다.

```
## jira | 작업 Jira

- [SHOP-100](https://example.atlassian.net/browse/SHOP-100) 주문 알림 비동기 전환 — Initiative
- [SHOP-112](https://example.atlassian.net/browse/SHOP-112) Mail Worker 구독자 추가 — Story
```

- 티켓 번호는 실제 Jira 주소로 링크한다 — 주소가 `…/browse/<그 키>` 가 아니면 WARN(L7)
- `— 유형`(Initiative·Epic·Story·Bug …)은 선택. Initiative 는 파란 칩으로 보인다
- Initiative 를 맨 위에, 그 아래 작업 티켓을 둔다
- 타이틀은 Jira 에 있는 그대로. 확인하지 못한 티켓은 넣지 않는다
- 화면에서 근거로 이어지는 링크는 이 절 하나다 — 출처 줄·파일 경로는 두지 않는다(L6)

## 용어 · L9 개발 용어는 직역하지 않는다 (WARN)

코드·설계 문서의 영어 용어를 한국어로 한 낱말씩 옮기면(직역) 처음 보는 사람은 그 말을 코드와 이어 읽지 못한다. "봉투"를 보고 envelope 을, "발산"을 보고 divergence 를 떠올리기는 어렵다. 개발 용어는 **현업에서 통하는 표기**로 쓴다.

| 원어 | 직역 (쓰지 않는다) | 쓰는 표기 |
|---|---|---|
| envelope | 봉투 | 담는 것의 이름(변경 집합·페이로드) |
| overlay | 덮기 | 오버레이 |
| point read | 점 읽기 · 점 조회 | 포인트 읽기 |
| divergence | 발산 | 불일치 |
| tombstone | 묘비 | 삭제 표시(tombstone) |
| shadow · probe | 가림 · 탐침 | 뜻으로 풀기(재조회 검증) |
| wiring | 결선 | 연결 |
| equivalence check | 동치 대조 | 일치 비교 |
| all-or-nothing | 전부 아니면 무 | 전부 커밋 또는 전부 취소 |
| drawer | 서랍 | 코드 이름 drawer — 처음 한 번 뜻을 괄호로: drawer(미리 정의된 질의). UI 패널이면 드로어 |
| hook | 갈고리 | 훅 |
| callback | 되부름 · 되부르기 | 콜백 |
| bucket | 양동이 | 버킷 |
| dead letter | 죽은 편지 | 데드레터(처리 못 한 메시지) |
| hot path | 뜨거운 경로 | 핫 패스(자주 타는 경로) |
| cold start | 차가운 시작 | 콜드 스타트 |

- 고르는 순서: 음차가 현업에서 통하면 음차(오버레이·포인트 읽기·청크·훅), 아니면 뜻이 드러나는 한국어 일반어(변경 집합·불일치·연결). 그 개념의 코드 이름이 화면의 다른 곳(도구 이름·설정 키)에도 나오면 코드 이름 그대로(drawer)
- 낯선 말은 처음 한 번만 원어나 코드 이름을 괄호로 붙인다 — "변경 집합(ChangeSet)", "창(window)". 두 번째부터는 한국어 표기만
- 코드 식별자(클래스·메서드·설정 키)와 도메인의 영문 고유 명칭은 번역하지 않는다
- 표에는 업무 글에서 원래 뜻으로 쓰일 일이 거의 없는 직역어만 둔다. 관로(pipeline)·상류(upstream)·탑재량(payload)처럼 어떤 업종에서는 제 뜻으로 쓰는 낱말은 넣지 않는다 — 오탐이 난다. 가구의 서랍장은 보지 않는다
- WARN(L9): AS IS ▶ TO BE · 성능 표 · 그림 라벨 · 흐름도 예시 · 이관 표의 항목·설명에 위 직역어가 있을 때. 작업 Jira 절은 티켓 원문 인용이라 보지 않는다. 같은 낱말을 원래 뜻(예: 수학의 발산)으로 썼다면 남겨도 된다 — 사람에게 보여 주고 정한다

## 약어 · L10 일반 IT 약어는 처음 나올 때 풀어 쓴다 (WARN)

개발자끼리 쓰는 약어는 처음 보는 사람에게 뜻이 없는 글자다. "상품 KB · 문서 저장소"를 보고 knowledge base 를 떠올리기는 어렵고, 오히려 용량 단위(킬로바이트)로 읽힌다. **처음 나올 때 한 번 풀어 쓰면** 그 뒤로는 약어만 써도 읽힌다.

| 약어 | 풀이 (예) | 약어 | 풀이 (예) |
|---|---|---|---|
| KB | 지식 베이스 | DTO | 데이터 전달 객체 |
| SSOT | 단일 정본 | PK · FK | 기본 키 · 외래 키 |
| PII | 개인 식별 정보 | DLQ | 실패 메시지 큐 |
| RU | 요청 단위 | ACL | 접근 제어 목록 |
| TTL | 유효 시간 | RBAC | 역할 기반 접근 제어 |
| SLA · SLO | 서비스 수준 협약 · 목표 | CQRS | 명령·조회 책임 분리 |
| RLS | 행 수준 보안 | RPO · RTO | 복구 시점 목표 · 복구 시간 목표 |
| ETL | 추출·변환·적재 | MTTR | 평균 복구 시간 |
| CDC | 변경 데이터 캡처 | IdP · IaC · PoC | 인증 제공자 · 코드형 인프라 · 개념 검증 |

- 글(AS IS ▶ TO BE · 성능 표 · 이관 표 · 흐름도 예시): 처음 나오는 곳에 바로 뒤 괄호 풀이 `KB(지식 베이스)` 나, 풀어 쓴 낱말 뒤 괄호 약어 `지식 베이스(KB)` 를 붙인다. 두 번째부터는 약어만
- 그림 라벨: 라벨은 짧아야 하므로 괄호 풀이를 달지 말고 **풀어 쓴 낱말로 바꾼다** — `상품 KB · 문서 저장소` → `상품 지식 베이스 · 문서 저장소`. 라벨보다 먼저 나오는 글에서 이미 풀었다면 라벨에는 약어를 써도 된다
- 풀이는 표의 낱말이 아니어도 된다 — 그 화면에서 뜻하는 대로 쓴다(ACL 이 접근 제어 목록이 아니라 다른 것이면 그 뜻으로)
- 대상은 이 표의 약어뿐이다. **도메인 약어(업종·규제 용어 — 예: 금융의 KYC, 의료의 ICD)와 코드 식별자는 보지 않는다** — 이 스킬은 도메인 영문 명칭을 번역하지 말라고 하므로, 대문자 낱말 전부가 아니라 목록 방식으로 판정한다. 표에는 다른 뜻으로 쓰일 일이 드문 일반 IT 약어만 둔다 — 검사기의 `ABBREVIATIONS` 와 이 표를 같게 둔다
- WARN(L10): 화면에 나오는 글(L6·L9 와 같은 영역 — 작업 Jira 절은 티켓 원문 인용이라 보지 않는다)을 **화면 차례대로**(AS IS ▶ TO BE → 성능 표 → 이관 표 → 관점마다 그림 라벨 → 흐름도 예시) 읽어, 표의 약어가 풀이 없이 나온 곳을 풀이가 나올 때까지 모두 알린다 — 처음 나온 곳을 풀면 그 뒤의 알림은 함께 사라진다. 같은 줄 안에 풀이가 있으면 풀린 것으로 본다. 괄호 안이 글자로 시작하지 않으면(`KB(34개)`) 풀이가 아니다
- 보지 않는 것: `코드` 표기 안 · 영문·숫자·`_`·`-` 에 붙은 코드 이름(`PK_ORDER`·`order-PK`) · 티켓 키 모양(`ETL-12`) · 앞에 숫자가 있는 KB(`512 KB` — 용량 단위). 한글 조사가 붙은 `KB를` 은 본다. 같은 글자를 다른 뜻(나라 코드·고유 명칭)으로 썼다면 남겨도 된다 — 사람에게 보여 주고 정한다
